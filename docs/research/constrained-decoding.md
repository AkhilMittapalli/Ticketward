## EXECUTIVE SUMMARY

**How Ollama applies `format` today**

- Since **v0.30.0 (2026-05-13)**, Ollama runs GGUF models through llama.cpp's `llama-server`.
- `format: <JSON Schema>` is forwarded to llama-server (`json_schema` on the completion path, `response_format` on the chat path).
- Constraint behaviour is therefore **exactly llama.cpp's JSON-Schema→GBNF converter**, with its documented limits:
  - unsupported keywords are *skipped silently*;
  - nested `$ref` is broken;
  - `minimum`/`maximum` apply to integers only;
  - no `uniqueItems`, `not` or `if/then`;
  - string repetition is capped at 2000.
- Ollama exposes **no raw GBNF parameter**. GBNF is only reachable by calling llama-server directly.

**Three traps affect our contract as written**

1. Pydantic emits `$defs`/`$ref` for every enum and for `Entity`. llama.cpp issue #21228 (open) reports that such schemas can **silently fail** (HTTP 200, schema-violating JSON). **Inline every `$ref`.**
2. llama.cpp orders **required properties first, then optional ones**. Our defaulted fields (`secondary_intents`, `churn_signals`, `entities`) are not in `required`, so the grammar **moves them after `rationale` and makes them optional**. That diverges from the "fixed key order" training target. **Generate the decoding schema in serialization mode with `json_schema_serialization_defaults_required=True`** so every key is required and ordered.
3. `churn_signals` items have no `maxLength`, so an unbounded string can run to `num_predict`.

**vLLM (production path)**

- The backends are `xgrammar`, `guidance` (llguidance), `outlines` and `lm-format-enforcer`, with default `auto`.
- The request field is `structured_outputs={"json": …}` or OpenAI `response_format`.
- The old `guided_json` / `guided_decoding_backend` fields were **removed in v0.12.0**. The latest release is v0.30.0 (2026-09-22).

**Accuracy and latency effects (literature)**

- Format restrictions can hurt *reasoning* (Tam et al. 2024).
- A 2025 benchmark found constrained decoding *improved* downstream accuracy across frameworks (JSONSchemaBench).
- XGrammar reports near-zero serving overhead.
- llama.cpp uses **sample-then-verify** (grammar rejection sampling), so a fine-tuned model that already emits the trained JSON pays little grammar overhead.
- Every JSON key token is still decoded one step at a time (no jump-forward in llama.cpp), which affects CPU latency.

## FINDINGS

### Q1. Ollama `format`: what actually happens and what is supported

**History**

- Structured outputs arrived in **v0.5.0 (2024-12-04)**: "provide a JSON schema object in the `format` parameter".
- v0.7.0 "Fixed issue where providing large JSON schemas in structured output requests would result in an error".
- v0.12.5: thinking models support structured outputs via `/api/chat`.
- v0.21.1: "Fixed structured outputs for Gemma 4 when `think=false`".
- v0.31.2 (2026-07-06): "Fixed structured output for thinking models when thinking is disabled".
- v0.34.4 (2026-09-23): "Structured outputs on thinking models now apply in a single pass".
- Source: [Ollama releases](https://github.com/ollama/ollama/releases), accessed 2026-09-26.

**Implementation (v0.30+)**

The header of `llm/llama_server.go` says ([source](https://github.com/ollama/ollama/blob/main/llm/llama_server.go), accessed 2026-09-26):

> "llama_server.go wraps the llama-server binary as a subprocess … For structured output, a JSON schema is passed to llama-server via its json_schema field and the "json" format as a builtin grammar via the grammar field. A format that applies after a response's thinking is sent as a grammar built around the GBNF llama-server itself derives from the schema."

- The completion request struct carries `Grammar`, `JsonSchema` and `NProbs`.
- The chat path sends `response_format: {"type":"json_schema","json_schema":{"name":"schema","schema":…}}`.
- **Raw mode:** in `server/routes.go`, "A raw prompt gives no way to tell where the response starts, so the format applies from its first token" (v0.34.4 source).

**Ollama docs** ([Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs), accessed 2026-09-26):

- Pass `format=Model.model_json_schema()`.
- "It is ideal to also pass the JSON schema as a string in the prompt to ground the model's response."
- "Lower the temperature (e.g., set it to `0`)".
- "Ollama's Cloud currently does not support structured outputs."

**llama.cpp support limits**

The converter supports "a subset of https://json-schema.org/". Known limitations, quoted from [grammars/README.md](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md), accessed 2026-09-26:

- "`additionalProperties` defaults to `false`"
- "Unsupported features are skipped silently"
- "Can't mix `properties` w/ `anyOf` / `oneOf` in the same type"
- "`prefixItems` is broken"
- "`minimum`, `exclusiveMinimum`, `maximum`, `exclusiveMaximum`: only supported for `"type": "integer"`"
- "Nested `$ref`s are broken (#8073)"
- "patterns must start with `^` and end with `$`"
- "string formats lack `uri`, `email`"
- "No `patternProperties`"

Unsupported and "unlikely to be implemented": `uniqueItems`, `contains`/`minContains`, `$anchor`, `not`, and `if`/`then`/`else`/`dependentSchemas`.

The README also notes: "The JSON schema is only used to constrain the model output and is not injected into the prompt."

**Known failures with Pydantic-style schemas**

- [#21228](https://github.com/ggml-org/llama.cpp/issues/21228), **open** at access: "json_schema with $ref/$defs silently fails". The API returns HTTP 200 with schema-violating JSON; only a server log line ("number of rules … exceeds sane defaults") reveals it. Workaround: inline `$ref`/`$defs`.
- [#8073](https://github.com/ggml-org/llama.cpp/issues/8073): enums referenced via `$ref` produced arbitrary objects. Workaround: inline enums.
- [#25746](https://github.com/ggml-org/llama.cpp/issues/25746), closed via PR #28469: nested string `maxLength >= 2000` emitted unparseable GBNF (`MAX_REPETITION_THRESHOLD = 2000`).

**Property order and optionality** ([json-schema-to-grammar.cpp](https://github.com/ggml-org/llama.cpp/blob/master/common/json-schema-to-grammar.cpp), accessed 2026-09-26):

- `_build_object_rule` splits properties into `required_props` and `optional_props`, emits the required ones in schema order, then the optional ones as optional.
- Whitespace between tokens is permitted: `SPACE_RULE = "| \" \" | \"\\n\"{1,2} [ \\t]{0,20}"`.

**Mapping to `TriageModelOutput` (§6.2)**

| Feature used | Supported? | Note |
|---|---|---|
| String enums (`Intent`, `Priority`, `Sentiment`, `ChurnRisk`, `ProductArea`, `Queue`, `RecommendedAction`, `EntityType`) | Yes | Only if **inlined**. Pydantic emits `$ref` to `$defs`. |
| `list[Intent]` with `max_length=2`; `list[str]` with `max_length=5`; `list[Entity]` with `max_length=20` | Yes (`minItems`/`maxItems` via repetition) | `Entity` is a nested object with an enum `type` (nested `$ref` → inline) |
| `str` with `max_length=400` / `200` | Yes (`char{0,N}`) | Keep below 2000 |
| `bool` | Yes | |
| `extra="forbid"` → `additionalProperties: false` | Yes (already the default) | |
| "secondary intents ≠ primary, unique" | **No** | Post-validate |
| Defaults (`default_factory=list`) | Changes the grammar | The field becomes optional and moves to the end. Force required (Q5). |

### Q2. GBNF

- GBNF is llama.cpp's grammar format. It is used as `--grammar`/`--grammar-file` in llama-cli and llama-completion, and as the `grammar` field in llama-server. JSON Schema is passed as `json_schema` (completion endpoints) or inside `response_format` (`/chat/completions`) ([grammars/README](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)). Grammars can be tested against strings with `tests/test-gbnf-validator.cpp`.
- **Ollama does not expose GBNF.** `api/types.go` (v0.34.4) has `Format json.RawMessage` and no grammar field. Internally, Ollama builds GBNF only to wrap a schema after a thinking block (`llm/gbnf.go`, `thinkingGrammar`).
- **Inspecting the grammar llama-server derives.** Ollama asks llama-server for it by POSTing `/completion` with `json_schema` and `response_fields: ["generation_settings/grammar"]` (`schemaGrammar()` in `llm/llama_server.go`). We can use the same call in CI to snapshot and diff the exact grammar our schema produces (Decision §4).
- **Sampling behaviour** ([common/sampling.cpp](https://github.com/ggml-org/llama.cpp/blob/master/common/sampling.cpp), accessed 2026-09-26):
  - With `grammar_first=false`, the sampler samples first, then checks "if the sampled token fits the grammar (grammar-based rejection sampling)". It applies the grammar to the full candidate list only on rejection.
  - "backend sampling is not compatible with grammar, disabling".

### Q3. vLLM structured-output backends

From [vLLM Structured Outputs](https://docs.vllm.ai/en/latest/features/structured_outputs.html) and [docs source](https://github.com/vllm-project/vllm/blob/main/docs/features/structured_outputs.md), accessed 2026-09-26:

- Backends: `xgrammar`, `guidance` (llguidance), `outlines` and `lm-format-enforcer`. Select one with `--structured-outputs-config.backend`. The default `auto` "will try to choose an appropriate backend based on the details of the request".
- Request forms:
  - online: `extra_body={"structured_outputs": {"json": schema}}`, or `response_format={"type":"json_schema","json_schema":{"name":…,"schema":…}}`;
  - offline: `SamplingParams(structured_outputs=StructuredOutputsParams(json=schema))`.
  - `choice`, `regex`, `grammar` (EBNF) and `structural_tag` are also supported.
- "deprecated API fields which were removed in v0.12.0": `guided_json`, `guided_regex`, `guided_choice`, `guided_grammar`, `guided_whitespace_pattern`, `guided_decoding_backend`.
- Relevant release notes ([vLLM releases](https://github.com/vllm-project/vllm/releases)):
  - v0.17.0 (2026-03-07): "Full support for the Qwen3.5 model family … featuring GDN".
  - v0.26.0: "handle grammar compilation failures without crashing the engine".
  - v0.29.0: "unsupported pattern+length schemas rejected".
  - v0.30.0 (2026-09-22): "XGrammar `patternProperties`/`propertyNames`/`unevaluatedProperties`".
- The Qwen3.5 model card shows `vllm serve … --language-model-only`, which skips the vision encoder ([Qwen3.5-4B card](https://huggingface.co/Qwen/Qwen3.5-4B)).

### Q4. Effect on accuracy and latency

**Literature**

- **Tam et al. 2024**, "Let Me Speak Freely?" ([arXiv:2408.02442](https://arxiv.org/abs/2408.02442)): "a significant decline in LLMs reasoning abilities under format restrictions"; "stricter format constraints generally lead to greater performance degradation in reasoning tasks".
  - Counterpoint, a vendor blog from .txt ([Say What You Mean](https://blog.dottxt.ai/say-what-you-mean.html)): re-runs with matched prompts found structured generation matching or beating free-form. This is not peer-reviewed.
- **JSONSchemaBench**, Geng et al. 2025 ([arXiv:2501.10868](https://arxiv.org/abs/2501.10868); [HTML v3](https://arxiv.org/html/2501.10868v3)):
  - evaluated Guidance, Outlines, llama.cpp, XGrammar, OpenAI and Gemini;
  - "constrained decoding, regardless of the framework, achieves higher performance than the unconstrained setting" (Guidance ~3%);
  - llama.cpp "dynamically compute[s] their constraints during token generation, leading to minimal grammar compilation time".
- **XGrammar**, Dong et al. 2024 ([arXiv:2411.15100](https://arxiv.org/abs/2411.15100)): "up to 100x speedup over existing solutions" and "near-zero overhead structure generation in end-to-end low-LLM serving".
- **Grammar-Aligned Decoding**, Park et al., NeurIPS 2024 ([arXiv:2405.21047](https://arxiv.org/abs/2405.21047)): grammar-constrained decoding "can distort the LLM's distribution, leading to outputs that are grammatical but appear with likelihoods that are not proportional to the ones given by the LLM". This matters for confidence; see `confidence-calibration.md`.

All accessed 2026-09-26.

**Implications for Ticketward** (inference from the facts above, to be measured in P2):

- **Fine-tuned model (E4):** the target JSON is exactly what SFT trained. The rejection sampler will rarely reject, so accuracy impact and grammar overhead should be minimal. The constraint's job is to guarantee **validity** (M-04 first-pass ≥ 98%).
- **Zero-shot (E3):** the grammar prevents invalid JSON, but it can force the model off its preferred tokens. That makes E3 a fair floor, not a best case. Report E3 with and without the constraint for honesty.
- **Latency:** structure tokens (13 keys, quotes, commas) are still one decode step each. llama.cpp has no jump-forward decoding. Output length, not the grammar, dominates CPU time. Measure `eval_count` per triage in P2.
- **Field order:** labels come first and `rationale` last. This matches "rationale is not chain-of-thought" (§6.2) and lets confidence be read from the early tokens. Keep training and decoding order identical.

### Q5. Making the decoding schema match the training target

Pydantic ([ConfigDict docs](https://pydantic.dev/docs/validation/latest/api/pydantic/config/), accessed 2026-09-26):

- `json_schema_serialization_defaults_required`: "Whether fields with default values should be marked as required in the serialization schema" (new in v2.4). It is applied via `model_json_schema(mode='serialization')`.
- Pydantic lists `properties` in field-declaration order. That is also the order `model_dump_json()` writes, so the training target (compact JSON from `model_dump_json()`) and the grammar share one order when all fields are required.

### Q6. Raw prompts and thinking

- The Ticketward provider sends HF-rendered prompts with `raw: true` (see `gguf-export-and-ollama.md`). The grammar then constrains from the very first generated token. For Qwen3.5 the prompt already ends with the empty think block `<think>\n\n</think>\n\n`, so the first generated token must be `{`.
- Ollama's thinking-aware grammar wrapper is not used in raw mode (`thinkingClose` is only set when `!req.Raw`, per the routes.go source).

## DECISION / RECOMMENDATION

### 1. Decoding-schema generator (backend, shared with ml)

```python
# backend/src/ticketward/ml/decoding_schema.py
import json
from copy import deepcopy
from typing import Any
from pydantic import BaseModel

_ANNOTATIONS = {"title", "description", "examples", "default"}

def decoding_schema(model: type[BaseModel]) -> dict[str, Any]:
    """Schema for grammar-constrained decoding (llama.cpp via Ollama, vLLM).

    Requires model_config = ConfigDict(extra="forbid", json_schema_serialization_defaults_required=True)
    on the model and on every nested model, so all properties are required and keep declaration order.
    """
    raw = model.model_json_schema(mode="serialization")
    defs = raw.pop("$defs", {})

    def inline(node: Any) -> Any:
        if isinstance(node, list):
            return [inline(v) for v in node]
        if not isinstance(node, dict):
            return node
        if "$ref" in node:
            return inline(deepcopy(defs[node["$ref"].rsplit("/", 1)[-1]]))
        out: dict[str, Any] = {}
        for k, v in node.items():
            if k in _ANNOTATIONS:
                continue
            if k == "properties":           # property names may collide with annotation keys: keep all
                out[k] = {name: inline(sub) for name, sub in v.items()}
            else:
                out[k] = inline(v)
        return out

    schema = inline(raw)
    text = json.dumps(schema)
    assert "$ref" not in text and "$defs" not in text
    assert schema["required"] == list(schema["properties"]), "all keys required, declaration order"
    return schema
```

Contract changes to accompany it:

- Add `json_schema_serialization_defaults_required=True` to the `TriageModelOutput` and `Entity` configs.
- `churn_signals: list[Annotated[str, Field(max_length=120)]]` (SI-2).
- A `@model_validator(mode="after")` that dedupes `secondary_intents` and removes the primary intent. This is a repair-L1 action, counted in `repaired_l1`.

### 2. Ollama triage request (OllamaProvider)

```python
payload = {
    "model": model_tag,                       # e.g. "tw-triage-qwen35-2b-lora:0.1.0"

if resp.get("done_reason") == "length":       # truncated JSON -> invalid -> repair L2 / fail closed

```

- `truncate`/`shift` default to true in the generate handler (`Truncate: req.Truncate == nil || *req.Truncate`, v0.34.4 source).
- With `truncate: false`, the llama-server runner skips its keep-`num_keep` middle-drop truncation. The expected result is an error for oversized prompts. **UNVERIFIED end-to-end**; add an integration test with a 10k-token prompt.
- `num_predict: 512` is a recommendation. The spec estimates 120–220 output tokens; 512 leaves headroom for 20 entities plus a 400-char rationale.

Neutralize the model's special-token literals in untrusted text before rendering. **Verify** with a red-team fixture.
